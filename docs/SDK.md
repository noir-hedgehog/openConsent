# SDK integration guide

openConsent `0.4.0-beta.1` uses one purpose-based decision model across Plain HTML, React, Vue, Express, and Spring Boot. The browser SDK owns the Banner, Preference Center, stored choices, explicit managed tags, Global Privacy Control (GPC), and purpose-level callbacks. Server adapters evaluate the same purpose IDs against request and receipt data supplied by the application.

## Choose an integration

| Application | Start with | Use it for |
| --- | --- | --- |
| Plain HTML, static site, or any frontend | `@openconsent/web` IIFE | One-script setup and automatic Banner |
| JavaScript or TypeScript frontend | `@openconsent/web` ESM | Programmatic setup and lifecycle control |
| React | `@openconsent/react` | Provider, Banner, gates, and hooks |
| Vue 3 | `@openconsent/vue` | Plugin, Banner, gates, and composable |
| Express | `@openconsent/express` | Server-observed decisions and GPC |
| Spring Boot 3 / Java 17 | `packages/spring-boot-starter` | Filter and server evaluator |

The JavaScript packages are prepared for the public `@openconsent` npm scope. Until the first tagged release is visible on npm, use repository builds or package tarballs generated by the release checks.

## Plain HTML

Place the browser script before any optional vendor code:

```html
<script
  src="https://noir-hedgehog.github.io/openConsent/openconsent.min.js"
  data-openconsent-config="/openconsent.json">
</script>
```

Register a script as inert markup so the browser cannot request it before a decision:

```html
<script
  type="text/plain"
  data-openconsent-purpose="optional-analytics"
  data-openconsent-src="https://example.com/analytics.js"
  data-openconsent-cleanup="stopAnalytics">
</script>
```

Only known purpose IDs from the active policy can activate a managed script. Unknown or stale purposes remain blocked.

This official hosted build is available before the npm launch. Once `@openconsent/web@0.4.0-beta.1` is published, the equivalent jsDelivr URL will be `https://cdn.jsdelivr.net/npm/@openconsent/web@0.4.0-beta.1/dist/openconsent.min.js`.

For external managed scripts, the vendor endpoint must permit a CORS fetch and satisfy your CSP, because openConsent downloads the code first and checks that consent is still valid immediately before execution.

## Browser API

```bash
pnpm add @openconsent/web@0.4.0-beta.1
```

```js
import { init } from '@openconsent/web';

const consent = init({
  projectId: 'my-app',
  locale: 'en',
  policy,
  banner: { position: 'bottom', theme: 'auto', privacyPolicyUrl: '/privacy' },
  onPreferenceChange(receipt) {
    navigator.sendBeacon(
      '/api/privacy/preferences',
      new Blob([JSON.stringify(receipt)], { type: 'application/json' })
    );
  }
});
```

The browser SDK:

- treats optional purposes as denied when there is no valid saved preference;
- stores a versioned preference record in `localStorage`;
- invalidates saved choices when the policy or notice version changes;
- enforces browser-observed GPC for sale/sharing purposes;
- activates explicitly registered tags only when their purpose is allowed;
- prevents new managed requests after withdrawal;
- emits an unsigned preference receipt to the callback.

The receipt is a transport object, not audit proof. A production backend must validate its schema, bind it to an authenticated or pseudonymous subject where appropriate, store it under access and retention controls, and record server-side timestamps and policy versions.

## Google Analytics 4 and Google Ads website example

Google support is application example code in `apps/demo`. It is not bundled into `@openconsent/web` and is not part of the SDK API. The example maps website purposes to Google Consent Mode fields:

| Integration | Purpose | Consent Mode fields |
| --- | --- | --- |
| GA4 | `optional-analytics` | `analytics_storage` |
| Google Ads | `personalized-ads` | `ad_storage`, `ad_user_data`, `ad_personalization` |

An application adapter should:

1. create the Google command queue and write denied defaults before loading a Google tag;
2. subscribe to the openConsent client or `openconsent:change`;
3. load `gtag.js` only when the application's matching purpose evaluates to `allow`;
4. send denied updates when the purpose is withdrawn;
5. test first visit, purpose-only grant, withdrawal, GPC, and command order;
6. publish the resulting Google Cookies in the deployment's own Cookie declaration.

Do not add an unconditional Google snippet. That bypasses purpose control and can send a request before the visitor decides. Measurement IDs belong to application configuration, never the reusable openConsent policy. Follow [Google's Consent Mode guide](https://developers.google.com/tag-platform/security/guides/consent) and verify the account and regional configuration independently.

## Shared core

```js
import { createOpenConsent } from '@openconsent/core';

const client = createOpenConsent({ policy });

client.evaluate('optional-analytics'); // deny by default
client.setChoice('optional-analytics', 'granted');
client.evaluate('optional-analytics'); // allow
client.setGpc(true);
client.evaluate('personalized-ads'); // deny when mapped to sale/sharing
```

`@openconsent/core` is framework-neutral and does not touch the DOM, load scripts, or create an evidence store.

## React

```bash
pnpm add @openconsent/react@0.4.0-beta.1 react
```

```jsx
import {
  OpenConsentProvider,
  ConsentBanner,
  ConsentGate
} from '@openconsent/react';

export function App() {
  return (
    <OpenConsentProvider options={{ policy }}>
      <ConsentBanner locale="en" />
      <ConsentGate purpose="optional-analytics">
        <Analytics />
      </ConsentGate>
    </OpenConsentProvider>
  );
}
```

`ConsentGate` prevents its child from mounting before an allowed decision. It cannot undo an earlier inline tag, preload, server event, or request created outside the gate.

In a browser, the provider uses `@openconsent/web` by default, so stored preferences, managed scripts, GPC, and purpose callbacks use the same runtime as Plain HTML. Application-owned vendor adapters may subscribe to that client. Pass `runtime: 'memory'` only for SSR or isolated tests, or supply your own `client`.

## Vue 3

```bash
pnpm add @openconsent/vue@0.4.0-beta.1 vue
```

```js
import { createApp } from 'vue';
import {
  createOpenConsentPlugin,
  ConsentBanner
} from '@openconsent/vue';

const app = createApp(App);
app.use(createOpenConsentPlugin({ policy }));
app.component('OpenConsentBanner', ConsentBanner);
app.mount('#app');
```

Use the package composable for purpose decisions and preference actions inside application components.

The Vue plugin also selects the browser runtime by default and falls back to the memory runtime during SSR. `runtime: 'memory'` remains available for explicit test setups.

## Express

```bash
pnpm add @openconsent/express@0.4.0-beta.1 @openconsent/core@0.4.0-beta.1 express
```

```js
import { openConsent, requirePurpose } from '@openconsent/express';

app.use(openConsent({
  policy,
  getSnapshot: async (req) => receiptStore.read(subjectFor(req))
}));

app.post(
  '/analytics',
  requirePurpose('optional-analytics'),
  analyticsHandler
);
```

The middleware reads `Sec-GPC` and exposes the request decision API. The application must implement authentication, subject mapping, receipt validation, the authoritative store, and downstream withdrawal behavior.

## Spring Boot 3

The Java 17 starter includes `OpenConsentFilter`, `OpenConsentEvaluator`, and `OpenConsentDecision`. The filter records server-observed GPC as a request attribute.

```java
Map<String, OpenConsentPurpose> purposes = Map.of(
  "optional-analytics",
  new OpenConsentPurpose("optional-analytics", "consent", false, false)
);
OpenConsentEvaluator evaluator = new OpenConsentEvaluator("policy-2026-09-01", purposes);

OpenConsentDecision decision = evaluator.evaluate(
  "optional-analytics",
  receipt.policyVersion(),
  gpc,
  choices
);

if (!decision.allowed()) {
  throw new ResponseStatusException(HttpStatus.FORBIDDEN);
}
```

Wire the evaluator to the authenticated subject and receipt repository before using a decision as an authorization guard. The starter is not yet published to Maven Central.

## Production security boundary

- Browser state and client-supplied receipts are untrusted input.
- Optional processing fails closed when preferences are missing, invalid, or stale.
- GPC observed by the server overrides a historical grant for configured CCPA sale/sharing purposes.
- Consent is one possible GDPR legal basis; do not use this API to relabel contract, legal obligation, or legitimate interests as consent.
- Production evidence needs protected immutable storage, subject resolution, version validation, signing or server attestation where appropriate, retention, access controls, and retryable downstream propagation.
- Explicit managed-tag blocking is not automatic website scanning or universal Cookie blocking.

## Publishing and provenance

JavaScript releases use a version tag such as `v0.4.0-beta.1`. The release workflow:

1. installs the locked workspace;
2. runs tests and package builds;
3. checks every public package with `npm pack --dry-run`;
4. publishes public packages with npm Trusted Publishing and provenance.

Prerelease versions such as `0.4.0-beta.1` use the npm `beta` dist-tag; stable versions use `latest`.

Before creating a release tag, a maintainer must:

- create or control the npm `@openconsent` organisation/scope;
- configure each package as public;
- add this GitHub repository and `.github/workflows/release.yml` as the npm Trusted Publisher;
- ensure the tag version exactly matches every public package version;
- review the dry-run file lists for accidental source, secret, fixture, or development-file inclusion.

The workflow uses GitHub OIDC and does not require a long-lived npm token. npm scope creation and Trusted Publisher configuration remain maintainer-controlled external steps.

## Conformance

`packages/protocol/conformance.json` defines shared decision fixtures. Release checks cover default denial, saved-choice restoration, withdrawal, stale-policy failure, GPC override, unknown-purpose blocking, idempotence, accessibility, and package contents. Google command ordering is tested as official-website example behavior rather than SDK conformance.
